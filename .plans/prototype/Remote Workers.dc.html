T3Code / t3o · remote workers

Remote workers and load-balanced placement

Workers are headless machines that join a board with a one-time code, then connect out to it and take its cards. The board knows only what each worker reports: its status, the headroom it offers, provider quota, and readiness per project. It never knows or shows whether a worker serves anything else. Cards are placed when their build starts, and every card carries a resource size. Planning always runs on the board server. This replaces Distributed Board's pairing flow; moving cards works as described there.

Status colours Blue · running, preparing, queued, waiting for a join Violet · waiting on a person Amber · blocked until something changes Green · Done cards only Grey · steady or neutral (connected, ready, joined, not placed)

Nothing animates. Running is a still blue dot, and progress is a stepped bar or a count that changes when the server reports. Finished stages, ready checkouts and a successful join get a grey tick: green belongs to Done cards only.

1Read-only capacity. Bars show capacity in use (ink) against what the worker declares, and the bold number is the free headroom it offers this board. The board doesn't ask why a worker offers less than it has free, and doesn't say. Hovering a bar shows “Declared 32 cores · offered 4 · this board's cards hold 24”. The hint has no edit link because the board can't reach in; the command copies on click.
2Set up on the board server appears inside This server's row whenever a project isn't set up there. It's amber, and shown before any worker problem, because planning for that project is stopped. Set up runs the project's setup stages on the board server, then its readiness script. The row reads “Cloning · 40%” in blue until it's done.
3Signed-in account. Each worker reports, for every provider, the account its CLI is signed in as and that account's plan, read from the worker's own login (claude login, codex login). It sits under that provider's quota bar, so you can see whose quota a percentage belongs to. Here build-02 runs on a personal account, which explains why its Codex quota is nearly gone while build-01's isn't. The board only displays the account; to change it, sign in again on the worker. If a provider is signed out, its line turns violet, “Signed out · run claude login on build-02”, and the planner skips that provider on that worker until it reports a login. Offline workers show the last reported account with “as of”.
·Re-check re-runs the project's readiness script (7) in the existing checkout, and the row reads “Checking…” in blue until it exits. Set up on worker clones and runs setup on that worker. Both are disabled while the worker is offline, with the tooltip “Available when mac-mini reconnects”. Clicking a not-ready row expands the script's full output.

Readiness script

A script the project keeps in its repo that answers one question: can this machine take z5 cards? T3o runs it in the project checkout on each worker and on the board server, after setup, on Re-check, and after T3o updates. Exit 0 means ready. Anything else means not ready, and the script's output is shown as the reason.
